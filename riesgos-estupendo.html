Bienvenido al Análisis Interactivo de la Modernización

Esta aplicación te guiará a través del Anexo Técnico para la modernización del aplicativo "Estupendo". El objetivo es transformar la plataforma actual Esdinamico SAS v1.0 hacia Estupendo 2.0, optimizando la experiencia de usuario, mejorando la escalabilidad y eficiencia, y automatizando la comunicación con clientes mediante APIs y una arquitectura de microservicios en AWS.

Esta transformación es fundamental para permitir que la plataforma maneje altos volúmenes de datos, como el procesamiento de hasta dos millones de documentos mensuales, y garantice la disponibilidad de documentos en menos de cinco segundos para su consulta. Explora las diferentes secciones utilizando la navegación para comprender la arquitectura actual, la visión de futuro, las tecnologías implicadas y los puntos clave de análisis.

Arquitectura Actual: Esdinamico SAS v1.0 - Un Monolito en Evolución

La plataforma actual de Esdinamico SAS v1.0 se centra en el procesamiento de documentos electrónicos de facturación y nómina. Está basada en un modelo MVC en PHP y ya utiliza varios servicios de AWS. Esta sección detalla sus componentes, funcionalidades y contexto operativo, revelando las bases sobre las que se construirá la modernización.

1.1. Módulos Funcionales y Sus Interdependencias

La arquitectura lógica se organiza en tres módulos principales, con interconexiones que sugieren un acoplamiento significativo:

  • Emisión: Gestiona creación, anulación, edición y seguimiento de facturas electrónicas, cumpliendo normativas DIAN. Incluye Configuración, Panel Administrativo (interno), Estadísticas (externo), Gestión de Documentos, Documentos Enviados y Reportes (rechazados, lista negra, CUFE).
  • Recepción: Administra documentos electrónicos y físicos recibidos. Submódulos: Configuración (carga, flujos, usuarios, proveedores), Panel Administrativo (redirige a Emisión), Estadísticas, Cargar documentos, Bandeja de Entrada y Reportes (erróneos, eventos).
  • Nómina: Provee herramientas para generación de soportes de pago y gestión de nómina. Submódulos: Configuración (perfil, usuarios, empleados), Gestión de Nómina (creación, ajustes) y Reportes.

La interconexión de paneles administrativos y la centralización de configuraciones son características de esta arquitectura monolítica, un desafío clave para la migración a microservicios.

1.2. Desglose a Nivel de Componentes (Modelo MVC PHP)

Desarrollada en PHP con patrón MVC, la plataforma se desglosa en componentes con responsabilidades amplias, lo que implica una base de código compleja y con posible deuda técnica:

  • Módulo de Manejo de Perfiles: Creación, actualización y gestión de perfiles de usuario. Interfaces: API de Gestión de Perfiles, BD de Usuarios, UI, Servicio de Autenticación.
  • Módulo de Emisión: Genera y emite documentos electrónicos (facturas, notas). Controladores como `ApiController` orquestan generación de XML, envío a DIAN, manejo de respuestas, y almacenamiento. `Attach Document` recibe respuestas DIAN, `Email Utilities` maneja envíos y validaciones.
  • Módulo de Recepción: Gestiona recepción, procesamiento y almacenamiento de documentos. Interfaces: `ApiRac Controller` y `Documentarse Controller` (recepción XML directa), Servicio de Correo, Validador, BD, Notificador.
  • Módulo de Nómina: Procesa y almacena pagos de nómina y ajustes. Interfaces: `Nómina ApiController` (recepción/validación DIAN), `Ajuste Nómina ApiController`, Generador de Documentos (`ApaRece Controller`), `Email Utilities`, `Document Controller`.

La presencia de "controladores gordos" con múltiples responsabilidades es un patrón común en monolitos. La reescritura de esta lógica a Python/Node.js implica riesgos de nuevas incidencias y retrasos, requiriendo una estrategia robusta para asegurar la paridad funcional y evitar un "monolito distribuido".

1.3. Huella de Despliegue Existente y Servicios AWS Utilizados

La plataforma ya utiliza un conjunto significativo de servicios AWS, lo que indica una inversión previa en la nube:

  • Application Load Balancer (ALB): Balancea la carga entre instancias EC2.
  • Instancias EC2: Alojan contenedores, backend y lógica de negocio, comunicándose con MongoDB.
  • ECS (Elastic Container Service): Ejecuta tareas específicas en contenedores.
  • S3 (Simple Storage Service): Almacena archivos estáticos (facturas, reportes).
  • CloudWatch: Monitorea logs, métricas y genera alarmas.
  • Roles de IAM: Controlan el acceso a servicios y recursos AWS.
  • CodePipeline, CodeCommit, CodeBuild, CloudFormation: Indican capacidades existentes de CI/CD e IaC.
  • SNS (Simple Notification Service) y SQS (Simple Queue Service): Para notificaciones y tareas asincrónicas.
  • Secrets Manager: Almacena credenciales sensibles.
  • Route 53: Gestiona el DNS.

La ambigüedad sobre la continuidad de AWS CodeSuite frente a Github Actions para el nuevo proyecto es un riesgo de fragmentación de CI/CD que debe ser abordado.

1.4. Gestión de Datos y Visión General de Seguridad

El Gestor de Datos es responsable del almacenamiento, organización y gestión de la información de documentos electrónicos. Utiliza MongoDB (probablemente Atlas, ya que se mantendrá).

  • Responsabilidades: Almacenamiento de documentos, gestión de transacciones, integridad de datos, protección de datos sensibles, acceso autorizado, recuperación y reportes.
  • Interacciones: API de Datos, Base de Datos, Servicios de Seguridad, Interfaces de reportes.
  • Seguridad Actual: Autenticación de usuarios, cifrado "en tránsito y en reposo", con "encriptación de contraseñas con Hash".

La falta de detalles sobre el cifrado de *todos* los datos sensibles (más allá de contraseñas) es una brecha crítica para datos financieros y de nómina bajo regulación de la DIAN. Se requiere un plan detallado de cifrado en reposo y gestión de claves.

Arquitectura Propuesta: Estupendo 2.0 - Hacia un Futuro Nube-Nativo

Estupendo 2.0 busca una transformación hacia una arquitectura desacoplada de microservicios nativa en AWS, con énfasis en la experiencia de usuario (UX) mediante Design Thinking. Esta sección detalla la visión arquitectónica, tecnologías y beneficios esperados, así como los desafíos inherentes a esta ambiciosa migración.

2.1. Objetivos Estratégicos y Beneficios de la Transición

Estupendo 2.0 busca potenciar la escalabilidad, optimizar la UX y flexibilizar la plataforma mediante servicios cloud-nativos de AWS. Mantendrá la robustez funcional, pero con componentes distribuidos y optimizados.

  • Escalabilidad Granular y Resiliencia: Escalado individual de servicios, tolerancia a fallos en múltiples Zonas de Disponibilidad de AWS.
  • Agilidad en Desarrollo y Despliegue: Despliegues autónomos y rápidos.
  • Eficiencia en Comunicación gRPC: Rendimiento optimizado para comunicación interna entre microservicios.
  • Contratos de Servicio Fuertes: Interfaces claras y tipadas.

El "Anexo Figma UX Estupendo 2.0" detallará la experiencia visual. El proceso de Design Thinking se integrará iterativamente en el desarrollo, requiriendo colaboración continua y validación de usuario para asegurar una plataforma robusta y adoptable.

2.2. Arquitectura Frontend: Especialización con Angular en AWS

Se implementarán aplicaciones frontend Angular distintas y autónomas para ofrecer experiencias de usuario especializadas, optimizar rendimiento y seguridad, y permitir ciclos de desarrollo ágiles.

Flujo de solicitud de usuario a través de la capa frontend.

  • Amazon S3: Alojamiento de artefactos estáticos (HTML, CSS, JS) con alta durabilidad y escalabilidad.
  • Amazon CloudFront: CDN global para baja latencia y reducción de carga, con caché en Puntos de Presencia.
  • AWS WAF: Firewall de aplicación web integrado con CloudFront para proteger contra vulnerabilidades comunes.
  • Amazon Route 53: Gestión de DNS para dirigir el tráfico a CloudFront.
  • AWS Certificate Manager (ACM): Gestión de certificados SSL/TLS para HTTPS.

La capa de Backend for Frontends (BFFs) es crucial para adaptar la API a las necesidades específicas de cada frontend, pero añade complejidad. Se requiere clarificación sobre sus responsabilidades (agregación, transformación, autenticación/autorización) y su implementación.

Las estrategias de autenticación/autorización diferenciadas para clientes y administración (posiblemente con Amazon Cognito) son complejas y requieren un plan detallado para SSO y gestión de identidad.

2.3. Arquitectura Backend: Microservicios con gRPC en AWS

Flujo de comunicación entre componentes backend y persistencia.

  • Descomposición Modular: Microservicios independientes (lista "archivo vivo").
  • Amazon VPC: Entorno de red aislado con subredes públicas/privadas, Gateways NAT, Grupos de Seguridad, NACLs.
  • Application Load Balancer (ALB): Punto de entrada para gRPC, balanceo de carga, chequeos de salud, terminación SSL.
  • Capa de Cómputo (EC2 / ECS / Fargate): Contenedores Docker gestionados por Amazon ECS.
  • AWS Auto Scaling: Escalado automático de instancias/contenedores.
  • Amazon ElastiCache for Redis: Caché en memoria de alta velocidad.
  • AWS IAM: Permisos granulares a recursos AWS.
  • Amazon CloudWatch: Recopilación de logs, métricas y alarmas.

La falta de un plan detallado de descomposición de microservicios es un riesgo de "monolito distribuido". Se necesita claridad en la metodología de descomposición y límites de servicio. Las estrategias de consistencia de datos (sagas, eventos) requieren detalle en implementación y manejo de errores.

2.4. Estrategia de Persistencia de Datos y Caché

La base de datos principal será Mongo Atlas, integrada de forma segura con la VPC de AWS. Se mantendrá la configuración actual, optimizando consultas.

  • Base de Datos Principal: Mongo Atlas (NoSQL gestionado externamente), con conexión segura y de baja latencia vía VPC Peering/PrivateLink/NAT Gateway.
  • Caché (ElastiCache for Redis): Almacén en memoria de alta velocidad para caché de consultas frecuentes, sesiones de usuario, contadores (rate limiting) y potencialmente como broker de mensajes ligero.

El desafío es mantener una instancia única de MongoDB compartida entre microservicios sin clara partición y propiedad de datos, lo que puede limitar la independencia de los servicios (riesgo de "base de datos compartida"). Se debe clarificar la estrategia para la partición de datos, evolución del esquema y propiedad de los datos.

El uso de Redis como "broker de mensajes ligero" requiere justificación frente a SQS/SNS para comunicaciones asíncronas robustas.

Flujo de integración y despliegue continuo.

  • CI/CD Frontend: Github Actions para construir y desplegar Angular en S3, invalidar caché en CloudFront.
  • CI/CD Backend: Herramientas para construir imágenes Docker y desplegar en ECS/EKS.
  • Infraestructura como Código (IaC): CloudFormation para gestionar recursos AWS.
  • Observabilidad: Amazon CloudWatch para logs, métricas y alarmas.
  • Calidad de Código: SonarQube para validación.

La ambigüedad entre AWS CodeSuite y Github Actions para CI/CD introduce riesgo de complejidad y fragmentación. Se necesita una estrategia unificada o justificación clara. CloudWatch básico es insuficiente para microservicios; se requiere rastreo distribuido (AWS X-Ray) y APM para observabilidad profunda.

2.6. Medidas de Seguridad y Cumplimiento Mejoradas

Se contempla un módulo de seguridad dedicado para proteger la información, controlar el acceso y detectar intrusiones.

  • Autenticación API: JWT, API Keys.
  • Encriptación: HTTPS para todas las comunicaciones.
  • Rate Limiting: Propuesta de 1000 req/min/cliente (necesita validación y flexibilidad).
  • Control de Acceso: Doble autenticación, módulo transversal de control de acceso, gestión de roles y perfiles.

Servicios de Seguridad AWS utilizados: IAM, Secrets Manager / Parameter Store, AWS WAF, Grupos de Seguridad VPC y NACLs, ACM.

Preocupaciones: Rate limiting fijo es insuficiente para protección DDoS integral. Necesidad de detalles concretos sobre cifrado de *todos* los datos sensibles en reposo (MongoDB, S3, EBS) y gestión de claves (AWS KMS), no solo hashing de contraseñas, para cumplir con la normativa DIAN.

2.7. Experiencia de Usuario (UX) y Estrategia de API

La estrategia UX se centra en un proceso de Diseño Centrado en el Humano (Design Thinking, personas, user journeys, prototipos Figma, pruebas de usabilidad), consolidado en el "Anexo Figma UX Estupendo 2.0".

La plataforma proporcionará APIs RESTful para interacción con clientes y webhooks para retroalimentación automática.

  • APIs RESTful Propuestas: Facturación (`GET /api/facturas`, `POST /api/facturas`), Pagos (`GET /api/pagos`), Reportes de Flujo de Caja (`GET /api/reportes/flujo-de-caja`), Notificaciones (`POST /api/notificaciones`).
  • Webhooks para Eventos: Factura Autorizada, Pago Registrado, Notificación de Recordatorio de Pago, estado de correo, eventos de recepción del adquirente, envío CUFE, cambio de estado de factura, entrega de documentos XML/PDF/ATTACHED.
  • Documentación API: Swagger/OpenAPI.

Se proponen mejoras en la API y funcionalidad para módulos existentes (Emisión, Recepción, Nómina, Reportes, Configuración, Panel Administrativo, Documentos Enviados/Recibidos) mediante migración a microservicios y nuevas APIs.

Puntos Críticos y Recomendaciones Clave para la Modernización

El análisis del anexo técnico revela varios puntos que requieren mayor clarificación y un plan de acción detallado por parte de la fábrica de software para mitigar riesgos y asegurar el éxito del proyecto. Haz clic en cada punto para ver más detalles.

1. Clarificación de la Estrategia de Descomposición de Microservicios

Problema: La descripción de módulos actuales y controladores PHP con amplias responsabilidades sugiere acoplamiento. La transición a microservicios necesita una metodología explícita para delimitar contextos de negocio y responsabilidades.

Recomendación: La fábrica de software debe presentar un plan detallado de descomposición que vaya más allá de un "archivo vivo". Incluir diagramas de contexto, límites de responsabilidad, estrategias para evitar acoplamiento (ej. no compartir BD directamente) y cómo se refactorizará la lógica de negocio de los "controladores gordos".

2. Estrategia de Consistencia de Datos en Entorno Distribuido

Problema: "Sagas y eventos" es un buen inicio, pero la implementación de transacciones distribuidas es compleja. Mantener MongoDB Atlas compartido sin particionamiento claro puede llevar a un "monolito de datos".

Recomendación: Explicar detalladamente la implementación de sagas/eventos (orquestación vs. coreografía), manejo de consistencia eventual, compensación de transacciones fallidas, idempotencia. Definir estrategia de propiedad de datos en MongoDB Atlas (¿BD/colecciones separadas por servicio? ¿Gestión de evolución de esquema?).

3. Consolidación y Madurez de la Estrategia de CI/CD

Problema: Coexistencia de AWS CodeSuite y propuesta de Github Actions introduce ambigüedad y riesgo de "dispersión de herramientas".

Recomendación: Definir una estrategia de CI/CD unificada y clara. Si se combinan herramientas, justificar y detallar orquestación, secretos, permisos y estandarización de pipelines.

4. Profundización en la Estrategia de Observabilidad

Problema: CloudWatch básico es insuficiente para la complejidad de microservicios.

Recomendación: Detallar planes para implementar rastreo distribuido (ej. AWS X-Ray, OpenTelemetry) y soluciones APM. Son cruciales para entender flujos de extremo a extremo, identificar cuellos de botella y diagnosticar problemas.

5. Detalles Concretos de Seguridad para Datos Sensibles

Problema: Afirmaciones sobre cifrado "en tránsito y en reposo" carecen de detalles más allá de hashing de contraseñas. Crítico para datos financieros/nómina (DIAN).

Recomendación: Plan detallado sobre cifrado de *todos* los datos sensibles en reposo (MongoDB, S3, EBS), mecanismos, gestión de claves (AWS KMS), clasificación de datos. Clarificar estrategia de rate limiting y defensa DDoS.

6. Definición de la Capa de Backend for Frontends (BFF)

Problema: BFFs como intermediarios entre frontends Angular y microservicios gRPC añaden complejidad que debe ser bien definida.

Recomendación: Especificar responsabilidades claras de los BFFs (agregación/transformación de datos, lógica frontend, autenticación/autorización), cómo se implementarán y cómo se gestionarán cuellos de botella o puntos únicos de fallo.

7. Riesgos de la Reescritura Completa de la Lógica de Negocio

Problema: La transición de PHP a Python/Node.js implica una reescritura completa de la lógica de negocio de los "controladores gordos" existentes. Esto conlleva riesgos de nuevas incidencias, retrasos en los plazos y dificultad para asegurar la paridad funcional con el sistema legado, especialmente si la lógica de negocio no está bien documentada.

Recomendación: La fábrica de software debe contar con una estrategia robusta para gestionar esta reescritura, asegurar la paridad de funcionalidades y planificar una migración por fases para minimizar cualquier interrupción operativa. La capacidad de identificar y extraer capacidades de negocio distintas de estos controladores existentes para formar microservicios verdaderamente independientes será fundamental para evitar la creación de un "monolito distribuido".

8. Falta de Detalle en Pruebas de Rendimiento y Carga

Problema: Aunque se mencionan requisitos críticos como el procesamiento de "dos millones de documentos mensuales" y la "disponibilidad en menos de cinco segundos", el anexo no detalla cómo se validarán estos requisitos en la nueva arquitectura. No hay mención explícita de pruebas de rendimiento, carga o estrés para asegurar que la solución cumpla con estas expectativas bajo condiciones de producción.

Recomendación: La fábrica de software debe presentar un plan de pruebas no funcionales que incluya pruebas de rendimiento, carga y estrés, así como los criterios de éxito y las herramientas a utilizar. Esto es crucial para validar que la nueva arquitectura puede soportar los volúmenes de datos y los requisitos de latencia esperados.

9. Plan de Desactivación del Sistema Legado y Coexistencia

Problema: No se aborda explícitamente cómo se realizará la transición del sistema PHP MVC existente. La falta de un plan claro para la desactivación o coexistencia puede introducir complejidades operativas y desafíos de sincronización de datos.

Recomendación: Se requiere un plan de migración detallado que aborde la coexistencia entre el sistema actual y el nuevo, la estrategia de migración de datos históricos (si aplica), y cómo se gestionarán los usuarios durante la transición. Esto incluye considerar estrategias como el "Strangler Fig Pattern" para una migración gradual.
