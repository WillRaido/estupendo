Bienvenido al Análisis Interactivo

Esta aplicación te guiará a través del Anexo Técnico para la modernización del aplicativo "Estupendo". El objetivo es transformar la plataforma actual Esdinamico SAS v1.0 hacia Estupendo 2.0, optimizando la experiencia de usuario, mejorando la escalabilidad y eficiencia, y automatizando la comunicación con clientes mediante APIs y una arquitectura de microservicios en AWS.

Explora las diferentes secciones utilizando la navegación para comprender la arquitectura actual, la visión de futuro, las tecnologías implicadas y los puntos clave de análisis.

Arquitectura Actual: Esdinamico SAS v1.0

La plataforma actual de Esdinamico SAS v1.0 se centra en el procesamiento de documentos electrónicos de facturación y nómina. Está basada en un modelo MVC en PHP y ya utiliza varios servicios de AWS. Esta sección detalla sus componentes, funcionalidades y contexto operativo.

1.1. Módulos Funcionales y Sus Interdependencias

La arquitectura lógica se organiza en tres módulos principales:

  • Emisión: Gestión de creación, anulación, edición y seguimiento de facturas electrónicas. Incluye submódulos de Configuración, Panel Administrativo, Estadísticas, Gestión de Documentos, Documentos Enviados y Reportes.
  • Recepción: Administración y control de documentos electrónicos y físicos recibidos. Incluye submódulos de Configuración, Panel Administrativo (compartido con Emisión), Estadísticas, Cargar documentos, Bandeja de Entrada y Reportes.
  • Nómina: Herramientas para generación de soportes de pago y gestión de nómina. Incluye submódulos de Configuración, Gestión de Nómina y Reportes.

La interconexión de paneles administrativos sugiere una naturaleza monolítica o acoplamiento significativo.

1.2. Desglose a Nivel de Componentes (Modelo MVC)

Desarrollada en PHP con patrón MVC, se desglosa en:

  • Módulo de Manejo de Perfiles: Creación, actualización y gestión de perfiles de usuario.
  • Módulo de Emisión: Generación y emisión de documentos electrónicos (facturas, notas). Utiliza controladores como `ApiController`, `Attach Document`, `Email Utilities`, `Radiant Controller`.
  • Módulo de Recepción: Gestión de documentos recibidos. Interfaces como `ApiRac Controller`, `Documentarse Controller`.
  • Módulo de Nómina: Procesamiento de pagos de nómina. Interfaces como `Nómina ApiController`, `Ajuste Nómina ApiController`.

La existencia de "controladores gordos" con múltiples responsabilidades es una característica de esta arquitectura monolítica.

1.3. Huella de Despliegue Existente y Servicios AWS Utilizados

La plataforma ya utiliza servicios de AWS como:

  • Application Load Balancer (ALB)
  • Instancias EC2 (alojando contenedores, backend y lógica de negocio)
  • ECS (Elastic Container Service) para tareas específicas
  • S3 (Simple Storage Service) para archivos estáticos
  • CloudWatch para monitoreo
  • Roles de IAM
  • CodePipeline, CodeCommit, CodeBuild, CloudFormation (para CI/CD e IaC)
  • SNS y SQS para notificaciones y tareas asíncronas
  • Secrets Manager
  • Route 53 para DNS

La presencia de CI/CD e IaC es una base sólida, aunque hay ambigüedad sobre su uso en el nuevo proyecto.

1.4. Gestión de Datos y Visión General de Seguridad

El Gestor de Datos es responsable del almacenamiento, organización y gestión de la información de documentos electrónicos. Utiliza MongoDB (probablemente Atlas, ya que se mantendrá).

Seguridad actual: Autenticación, cifrado "en tránsito y en reposo" (detalle específico: "encriptación de contraseñas con Hash").

La falta de detalles sobre el cifrado de todos los datos sensibles (más allá de contraseñas) es una brecha a considerar para datos financieros y de nómina.

Arquitectura Propuesta: Estupendo 2.0

Estupendo 2.0 busca una transformación hacia una arquitectura desacoplada de microservicios nativa en AWS, con énfasis en la experiencia de usuario (UX) mediante Design Thinking. Esta sección detalla la visión arquitectónica, tecnologías y beneficios esperados.

2.1. Objetivos Estratégicos y Beneficios

Objetivos: Escalabilidad, optimización UX, flexibilidad.

Beneficios esperados:

  • Escalabilidad granular y resiliencia con AWS.
  • Agilidad en desarrollo y despliegue.
  • Eficiencia en comunicación interna con gRPC.
  • Contratos de servicio fuertes.

Se espera un "Anexo Figma UX Estupendo 2.0" para detallar la experiencia visual y de interacción.

2.2. Arquitectura Frontend: Angular en AWS

Se implementarán aplicaciones frontend Angular distintas y autónomas para especializar la UX.

Servicios AWS para Frontend:

  • Amazon S3: Alojamiento de artefactos estáticos (HTML, CSS, JS).
  • Amazon CloudFront: CDN global para baja latencia y reducción de carga.
  • AWS WAF: Seguridad perimetral contra vulnerabilidades web comunes.
  • Amazon Route 53: Gestión de DNS.
  • AWS Certificate Manager (ACM):: Gestión de certificados SSL/TLS para HTTPS.

Los frontends consumirán servicios backend a través de APIs (BFFs - Backend for Frontends), que a su vez interactuarán con microservicios gRPC. Se necesitan clarificaciones sobre las responsabilidades y la implementación de los BFFs.

Se consideran estrategias de autenticación/autorización diferenciadas, posiblemente con Amazon Cognito.

2.3. Arquitectura Backend: Microservicios con gRPC en AWS

Núcleo transformado a microservicios con gRPC para comunicación interna.

Servicios AWS para Backend:

  • Descomposición Modular en Microservicios: Lista de microservicios será un "archivo vivo".
  • Amazon VPC: Entorno de red aislado con subredes públicas y privadas.
  • Application Load Balancer (ALB): Punto de entrada para gRPC, balanceo y terminación SSL.
  • Capa de Cómputo (EC2 / ECS / Fargate): Contenedores Docker gestionados por ECS.
  • AWS Auto Scaling: Escalado automático de instancias/contenedores.
  • Amazon ElastiCache for Redis: Caché en memoria para consultas, sesiones, rate limiting, y potencialmente broker ligero.
  • AWS IAM: Permisos granulares.
  • Amazon CloudWatch: Logs, métricas y alarmas.

Riesgo: La falta de un plan detallado de descomposición de microservicios puede llevar a un "monolito distribuido". Se necesita claridad en la metodología de descomposición y límites de servicio.

Se mencionan estrategias de consistencia de datos (sagas, eventos), pero requieren detalle en implementación y manejo de errores.

2.4. Estrategia de Persistencia de Datos y Caché

Base de Datos Principal: Mongo Atlas (servicio NoSQL gestionado externamente), integrado con VPC de AWS. Se mantendrá la configuración actual, optimizando consultas.

Caché: Amazon ElastiCache for Redis para consultas frecuentes, sesiones de usuario, contadores (rate limiting) y potencialmente como broker de mensajes ligero.

Desafío: Mantener una instancia única de MongoDB compartida entre microservicios sin una clara partición y propiedad de datos puede limitar la independencia de los servicios (riesgo de "base de datos compartida").

Se debe clarificar el uso de Redis como broker de mensajes frente a SQS/SNS.

2.5. DevOps, CI/CD y Marco de Observabilidad

Énfasis en automatización, entrega continua y monitoreo.

  • CI/CD Frontend: Github Actions para construir y desplegar Angular en S3, invalidar caché en CloudFront.
  • CI/CD Backend: Herramientas para construir imágenes Docker y desplegar en ECS.
  • Ambigüedad CI/CD: Mención de AWS CodeSuite (existente) y Github Actions (propuesto). Necesita unificación o justificación clara.
  • Infraestructura como Código (IaC): CloudFormation.
  • Observabilidad: Amazon CloudWatch para logs, métricas y alarmas.

Limitación: CloudWatch básico es insuficiente para microservicios. Se necesita rastreo distribuido (ej. AWS X-Ray) y APM para observabilidad profunda.

Calidad de código: SonarQube.

2.6. Medidas de Seguridad y Cumplimiento Mejoradas

Módulo de seguridad dedicado para proteger información, controlar acceso y detectar intrusiones.

  • Autenticación API: JWT, API Keys.
  • Encriptación: HTTPS para todas las comunicaciones.
  • Rate Limiting: Propuesta de 1000 req/min/cliente (necesita validación y flexibilidad).
  • Control de Acceso: Doble autenticación, módulo transversal de control de acceso, gestión de roles y perfiles.

Servicios de Seguridad AWS:

  • IAM, Secrets Manager / Parameter Store, AWS WAF, Grupos de Seguridad VPC y NACLs, ACM.

Preocupaciones: Rate limiting fijo es insuficiente para protección DDoS integral. Necesidad de detalles concretos sobre cifrado de *todos* los datos sensibles en reposo (MongoDB, S3, EBS) y gestión de claves (AWS KMS), no solo hashing de contraseñas.

2.7. Experiencia de Usuario (UX) y Estrategia de API

UX: Diseño Centrado en el Humano (Design Thinking, personas, user journeys, prototipos Figma, pruebas de usabilidad). Consolidado en "Anexo Figma UX Estupendo 2.0".

APIs RESTful propuestas:

  • Facturación (`GET /api/facturas`, `POST /api/facturas`)
  • Pagos (`GET /api/pagos`)
  • Reportes de Flujo de Caja (`GET /api/reportes/flujo-de-caja`)
  • Notificaciones (`POST /api/notificaciones`)

Webhooks para retroalimentación automática (Factura Autorizada, Pago Registrado, etc.).

Documentación API: Swagger/OpenAPI.

Mejoras propuestas a módulos existentes (Emisión, Recepción, Nómina, Reportes, Configuración, etc.) mediante migración a microservicios y nuevas APIs.

Puntos Críticos y Recomendaciones Clave

El análisis del anexo técnico revela varios puntos que requieren mayor clarificación y un plan de acción detallado por parte de la fábrica de software para mitigar riesgos y asegurar el éxito del proyecto. Haz clic en cada punto para ver más detalles.

1. Clarificación de la Estrategia de Descomposición de Microservicios

Problema: La descripción de módulos actuales y controladores PHP con amplias responsabilidades sugiere acoplamiento. La transición a microservicios necesita una metodología explícita para delimitar contextos de negocio y responsabilidades.

Recomendación: La fábrica de software debe presentar un plan detallado de descomposición que vaya más allá de un "archivo vivo". Incluir diagramas de contexto, límites de responsabilidad, estrategias para evitar acoplamiento (ej. no compartir BD directamente) y cómo se refactorizará la lógica de negocio de los "controladores gordos".

2. Estrategia de Consistencia de Datos en Entorno Distribuido

Problema: "Sagas y eventos" es un buen inicio, pero la implementación de transacciones distribuidas es compleja. Mantener MongoDB Atlas compartido sin particionamiento claro puede llevar a un "monolito de datos".

Recomendación: Explicar detalladamente la implementación de sagas/eventos (orquestación vs. coreografía), manejo de consistencia eventual, compensación de transacciones fallidas, idempotencia. Definir estrategia de propiedad de datos en MongoDB Atlas (¿BD/colecciones separadas por servicio? ¿Gestión de evolución de esquema?).

3. Consolidación y Madurez de la Estrategia de CI/CD

Problema: Coexistencia de AWS CodeSuite y propuesta de Github Actions introduce ambigüedad y riesgo de "dispersión de herramientas".

Recomendación: Definir una estrategia de CI/CD unificada y clara. Si se combinan herramientas, justificar y detallar orquestación, secretos, permisos y estandarización de pipelines.

4. Profundización en la Estrategia de Observabilidad

Problema: CloudWatch básico es insuficiente para la complejidad de microservicios.

Recomendación: Detallar planes para implementar rastreo distribuido (ej. AWS X-Ray, OpenTelemetry) y soluciones APM. Son cruciales para entender flujos de extremo a extremo, identificar cuellos de botella y diagnosticar problemas.

5. Detalles Concretos de Seguridad para Datos Sensibles

Problema: Afirmaciones sobre cifrado "en tránsito y en reposo" carecen de detalles más allá de hashing de contraseñas. Crítico para datos financieros/nómina (DIAN).

Recomendación: Plan detallado sobre cifrado de *todos* los datos sensibles en reposo (MongoDB, S3, EBS), mecanismos, gestión de claves (AWS KMS), clasificación de datos. Clarificar estrategia de rate limiting y defensa DDoS.

6. Definición de la Capa de Backend for Frontends (BFF)

Problema: BFFs como intermediarios entre frontends Angular y microservicios gRPC añaden complejidad que debe ser bien definida.

Recomendación: Especificar responsabilidades claras de los BFFs (agregación/transformación de datos, lógica frontend, autenticación/autorización), cómo se implementarán y cómo se gestionarán cuellos de botella o puntos únicos de fallo.

7. Riesgos de la Reescritura Completa de la Lógica de Negocio

Problema: La transición de PHP a Python/Node.js implica una reescritura completa de la lógica de negocio de los "controladores gordos" existentes. Esto conlleva riesgos de nuevas incidencias, retrasos en los plazos y dificultad para asegurar la paridad funcional con el sistema legado, especialmente si la lógica de negocio no está bien documentada.

Recomendación: La fábrica de software debe contar con una estrategia robusta para gestionar esta reescritura, asegurar la paridad de funcionalidades y planificar una migración por fases para minimizar cualquier interrupción operativa. La capacidad de identificar y extraer capacidades de negocio distintas de estos controladores existentes para formar microservicios verdaderamente independientes será fundamental para evitar la creación de un "monolito distribuido".

8. Falta de Detalle en Pruebas de Rendimiento y Carga

Problema: Aunque se mencionan requisitos críticos como el procesamiento de "dos millones de documentos mensuales" y la "disponibilidad en menos de cinco segundos", el anexo no detalla cómo se validarán estos requisitos en la nueva arquitectura. No hay mención explícita de pruebas de rendimiento, carga o estrés para asegurar que la solución cumpla con estas expectativas bajo condiciones de producción.

Recomendación: La fábrica de software debe presentar un plan de pruebas no funcionales que incluya pruebas de rendimiento, carga y estrés, así como los criterios de éxito y las herramientas a utilizar. Esto es crucial para validar que la nueva arquitectura puede soportar los volúmenes de datos y los requisitos de latencia esperados.

9. Plan de Desactivación del Sistema Legado y Coexistencia

Problema: No se aborda explícitamente cómo se realizará la transición del sistema PHP MVC existente. La falta de un plan claro para la desactivación o coexistencia puede introducir complejidades operativas y desafíos de sincronización de datos.

Recomendación: Se requiere un plan de migración detallado que aborde la coexistencia entre el sistema actual y el nuevo, la estrategia de migración de datos históricos (si aplica), y cómo se gestionarán los usuarios durante la transición. Esto incluye considerar estrategias como el "Strangler Fig Pattern" para una migración gradual.
